# 参考: DDP・工程順序・一般比較フレーム

## 本スキルでの「DDPモニタリング」寄りの読み方

厳密な組織定義のDDP（欠陥検出率の数式）が無い場合でも、Issueに **`最短で検出できたテスト工程`** と **`検出したテスト工程`** があるなら、次の**実務モニタリング**に落とす。

1. **シフトレフト余地（検出遅延）**  
   同一欠陥について、**最短工程が検出工程より上流**なら「より早い工程で取りこぼした／そこまで到達していない」シグナル。  
   - 最短が **仕様/設計レビュー** なのに検出が **結合/UAT** → 上流レビュー・単体・結合設計の強化候補。  
   - 最短が **単体** なのに検出が **探索** → ケース化・自動化・データ整備の候補。

2. **データ品質チェック**  
   「最短」が「検出」より**下流**になっている件は、**ラベル誤り**または**工程定義の不一致**の可能性。レポートに**件数と例（タイトル1〜2件）**を載げ、断定しない。

3. **検出工程の偏り**  
   探索的テストや結合に集中 → **計画テストのカバレッジ**・**リスクベースド**の配分見直しの話題に接続可能（参考扱い）。

## 工程順序の決め方（エージェント向け）

1. データから **`検出したテスト工程` と `最短で検出できたテスト工程` に出現するラベル**をユニオンする。  
2. **ユーザーが「今回のテスト工程の実施順」を明示した場合はそれを最優先**する（例: KJ 結合テストでは **①デザインレビュー → ②探索的テスト → ③結合テスト → ④UAT**。データ上の「結合テストケース」「動作確認」は③に含める、単体・仕様レビュー系は①より上流として -1 など、レポートにマッピング規則を明記する）。  
3. 明示がない場合のみ、出現ラベルに基づき**弱い順序（上流→下流）**のテンプレを当てはめる。`バグではない` / `検出不可` は比較対象外。  
4. レポートに**使用した順序・ラベルマッピング**を必ず書く。

## Statusの意味（ユーザー定義の反映）

- **完了**: 起票から最短で修正完了（初回の修正でクローズに近いイメージ）。  
- **再テスト完了**: 修正後のテストでNG → 再修正 → 完了。**リワーク・修正の切れ味・再現性・受入条件**の観点で読む（参考の改善案に回す）。

## 一般的なシステム開発との比較フレーム（定性のみ）

数値ベンチマークは**持ち込まない**。代わりに、次の**よくあるパターン**と照らして文章化する。

| 一般的傾向（文献・経験則レベル） | 本データの読み方 |
|----------------------------------|------------------|
| 上流要件・仕様の曖昧さは、後工程で「仕様不良」「仕様漏れ」として顕在化しやすい | `バグ発生理由` の仕様系と、`最短工程` がレビュー寄りの組み合わせを見る |
| 実装ミス・漏れは単体/結合で拾えることが多いが、状態・非機能・外部連携は抜けやすい | `状態管理` `外部接続` `ファイル操作` と工程ギャップ |
| 探索的テストで多発＝**想定外パス**や**複合条件**の不足、または計画ケースの未整備 | 検出工程が探索に偏る件のタイトル傾向（読み取れる範囲で） |
| UATで多発＝**本番相当データ/権限/外部**のギャップ、または本来結合で潰すべき欠陥 | 検出/UAT×分類 |
| 「原因不明」が多い＝ログ・再現手順・切り分けの不足のシグナルになりうる | 参考改善に記載 |

## バグ発生理由ラベルの粗いグルーピング例

レポートで色分け・積み上げに使える（データのラベルに合わせ調整）:

- **仕様・設計**: 仕様不良、仕様漏れ、仕様変更  
- **実装**: 実装ミス、実装漏れ  
- **検証・テスト**: テスト不良、調査/検証不足  
- **その他**: 原因不明、ライブラリ依存不良、デザイン漏れ、バグではない 等

## 出典・用語（ユーザー向け脚注用）

レポート末尾に短くよい:

- DDPは組織・定義により式が異なるため、本レポートのDDPは**「検出工程と最短工程のギャップ分析」**として扱った旨。
- 一般比較は**業界統計の引用ではなく**、QAの**一般的説明**として記載した旨。
