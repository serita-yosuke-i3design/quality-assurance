# 観点整理の考え方：機能単位の完結性と共通カテゴリ

## 結論（QAプロとしての見解）

1. **機能ごとに観点の漏れがないようにする**ことを最優先とするなら、**各機能で「その機能で確認すべきこと」が一覧で完結している**形が望ましい。
2. **共通カテゴリは必須ではない**。類似観点が各機能に重複して存在してもよい。重複より漏れ防止を優先する。
3. **機能観点と表示観点は分離する**。例：ログイン「機能」（認証・遷移・状態維持）と、ログイン「画面の表示」（レイアウト・ヘッダー・フッター等）を分けると、何をテストするかが明確になる。

---

## セルフレビューに基づく理由

### 1. 機能単位で完結させる利点

- テスト設計時に「この機能の観点」だけを見れば、漏れなくチェックリストを組み立てられる。
- 共通だけに書いてあると、「この機能で共通を適用するか」の判断が曖昧になり、適用漏れが起きやすい。
- 機能オーナーやテスト担当が「自分の機能の観点」を一箇所で完結して参照できる。

### 2. 共通を廃止してもよい理由

- 「共通」に書く観点（データ保持、レスポンシブ、レイアウト等）は、**どの機能でも「その画面・その操作で」確認する**もの。共通にだけ書くと、実際のテストでは「各機能のテスト時に共通も見る」という二重の参照になり、漏れが生じやすい。
- 共通をやめ、必要な観点を各機能に重複して持たせると、**一機能を見ただけで「この機能でやるべき確認」が揃う**。重複のデメリットより、漏れ防止のメリットの方が大きい。
- 共通カテゴリが「存在しなくてもよい」という意味は、**観点の設計の軸を「機能ごとの完結性」に置く**と、共通というまとまりは必須ではなくなる、という解釈でよい。

### 3. 機能と表示の分離

- 「ログイン機能」で確認したいのは、**認証が通るか・通らないか・その後どう遷移するか・状態がどう維持されるか**など、振る舞い（機能）である。
- ヘッダー・フッターの有無やレイアウトは、**ログインという機能の成否**ではなく、**ログイン画面の見た目・表示**の観点。同じ「01-ログイン」でも、観点のブロックとして「機能」と「表示」を分けておくと、「何をテストしているか」が明確になる。
- 他機能（一覧表示、登録・編集など）でも、**機能観点（振る舞い）** と **表示観点（レイアウト・項目表示等）** を分けておくと、表の一貫性と読みやすさが増す。

### 4. ログイン機能の観点の現実的な粒度

- ご提示の4項目（正しい情報でログインできるか、誤った情報でログインできないか、ログイン後の画面遷移、リロード・再起動後の状態維持）は、**認証の正常系・異常系・遷移・状態維持**を押さえた現実的な粒度**である。
- 既存の細かい観点（必須チェック、桁数チェック、認証エラーID/PW、セッション維持、直接URLアクセス等）は、これら4つの**確認内容・テストポイントとして具体化**すればよい。観点の「項目」を4本柱に整理し、中身（確認内容）で網羅性を保つ形が運用しやすい。

### 5. 共通を残す場合の使い分け

- 共通を残すなら、「全機能に共通して参照すべき観点の参照用リスト」に限定し、**テスト設計時には各機能のファイルに「本機能に必要な共通相当の観点」を列挙する**運用にすると、漏れが減る。
- それでも「機能ファイルだけ見て完結」にはならないため、**漏れ防止を最優先するなら、共通を廃止し各機能に必要な観点を重複して持たせる方針**を推奨する。

### 6. トレードオフの明示

- **共通を廃止し機能ごとに完結させる**：メンテで同じような観点を複数機能に書く手間は増える。一方で、機能単位の漏れ防止と、「この機能で何を見るか」の明確さが得られる。
- QAでは**漏れ防止の方がコストより重要**と考えるため、重複を許容してでも機能単位の完結性を優先する設計を支持する。

### 7. まとめ

- **基本前提**：機能ごとに観点の漏れがないようにする。
- **共通**：類似観点が各機能に重複して存在してもよい。共通というカテゴリは必須ではない。
- **ログイン**：「ログイン機能」観点（入力・認証・遷移・状態維持）と「ログイン画面の表示」観点（レイアウト、ヘッダー・フッター等）を分離し、機能観点は提示の4項目を軸に整理するのが現実的である。
