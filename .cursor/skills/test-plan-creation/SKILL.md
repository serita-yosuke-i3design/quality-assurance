# テスト計画書作成（対話ドリブン）

依頼を受けたら、**テンプレートを一括で埋めない**。リポジトリ・既存資料を読み、**何が分かっていて何が未決か**を整理し、ユーザーと**壁打ち**しながら計画書を育てる。**全文ドラフトはユーザーが明示的に了承するまで書かない**（トークン節約・誤合意防止）。

## プロジェクトプロファイル（Phase 0 必須）

[_shared/profile-resolution.md](../_shared/profile-resolution.md) に従う。

| profile キー | 用途 |
| --- | --- |
| `paths.test_plan` | 計画書本体 |
| `paths.decisions` | 未決・選択肢 |
| `paths.confirmations` | ステークホルダー向け確認リスト |
| `sources.requirements` | 要件入口 |

## このスキルでやること / やらないこと

**やる**

- テスト計画書に必要な**情報項目の棚卸し**と優先度付け
- 既存資料・コードから**確定事項の抽出**（推測は `【要確認】` と明記）
- **1回のレスポンスで質問は1〜2個**に絞った壁打ち
- 合意済みセクションのみ段階的にドラフト化
- `決定が必要な項目.md` / `確認事項一覧.md` と計画書の**双方向同期**
- 条件が固まるたびに**バージョン・更新履歴**を追記して改訂

**やらない（別スキルへ）**

- 機能×観点カバレッジ表の作成・改訂 → [viewpoint-coverage-matrix](../viewpoint-coverage-matrix/SKILL.md)
- テストケース・項目表の詳細生成 → [test-case-generation](../test-case-generation/SKILL.md)
- E2E 自動化の計画・設計 → [e2e-strategy-delivery](../e2e-strategy-delivery/SKILL.md)
- テスト完了レポート → [test-completion-report](../test-completion-report/SKILL.md)
- 要件そのものの最終決定（ファシリテーションと選択肢提示はする）

| profile キー | 用途 |
| --- | --- |
| `test_plan` | 本体 |
| `decisions` | 未決・選択肢・背景 |

## 作業フェーズ

### Phase 0: コンテキスト把握（初回・更新時）

ファイルを書き換える前に実施。

1. **既存の計画書**があれば読む（`paths.test_plan`、バージョン・更新履歴）
2. **仕様・設計の入口**を特定（`sources.*`、OpenAPI、画面一覧、README）
3. **既存テスト資産**の有無（設計書 10〜14、項目表、CI、観点表）
4. **未決トラッキング**（`paths.decisions` / `paths.confirmations`）を読む
5. **依頼の種類**を判定: 新規作成 / 部分更新 / 決定反映のみ

### Phase A: 情報棚卸し（既定・第1レスポンス）

**この Phase のみでレスポンスを終える。** 計画書全文・長大な表は出さない。

1. [information-checklist.md](information-checklist.md) の章ごとに **確定 / 一部 / 未着手** を判定
2. リポジトリから**根拠パス**を1行ずつ付ける（推測で「確定」にしない）
3. **次に聞くべき質問を1〜2個**に絞る（優先度 P0 → P1）
4. 全文ドラフトの可否を示し、了承を求める

**第1レスポンスは必ずこの形式**

```markdown
# テスト計画書 — 情報棚卸し

## 依頼の理解
（新規 / 改訂 / 反映範囲）

## 参照した情報
（パス・ファイル名）

## 章別の充足状況

| 章 | 充足 | 根拠・現状 | ドラフトに必要な追加情報 |
| --- | --- | --- | --- |
| 1. はじめに | 確定／一部／未 | | |
| 2. プロジェクト概要 | | | |
| 3. テスト戦略 | | | |
| 4. フェーズ概要 | | | |
| 5. 体制 | | | |
| 6. 環境 | | | |
| 7. 障害管理 | | | |
| 8. リスク | | | |
| 9. 承認 | | | |

**充足の意味**
- **確定**: 資料またはユーザー発言で合意済み
- **一部**: 骨格のみ。数値・一覧・方針の詳細が欠ける
- **未**: 情報なし。質問または `【要確認】` 前提

## いま優先して決めたいこと（P0）
（未決のうち、他章の前提になるものを最大3項目）

## 今回の質問（1〜2個に限定）
1. …
2. …

## 次のアクション
計画書の全文ドラフトは、上記の回答をいただいてから行います。
**どの章から書き始めますか？** または **まず決定事項だけ `確認事項一覧` に追記しますか？**
```

### Phase B: 部分ドラフト（ユーザー指示後）

ユーザーが「§3 だけ」「P0 が決まったのでドラフト」「全文」と**明示**した場合のみ。

**ルール**

- **合意済み**の記述のみ断定形。未決は `【要確認】` または `−`
- 推測でフェーズ名・合格率・担当者名を埋めない
- **1章ずつ**または**依頼範囲**に限定（「全文」指示でも未決章はプレースホルダー＋確認事項へ誘導）
- ドラフト末尾に **今回の未決リスト** を必ず付ける

### Phase C: ファイル反映（ユーザー了承後）

1. `paths.test_plan` を更新（既存があれば**差分更新**）
2. 未決は `paths.decisions` に背景・選択肢付きで追記
3. ステークホルダー確認用は `paths.confirmations` に要約行を追記
4. **更新履歴**にバージョン・日付・変更概要。ヘッダに **作成 Skill 版**を追記
5. ドキュメント構成図内のリンクは、**実在するファイル**にのみ張る

## 壁打ちの進め方

### 質問の優先順位

[information-checklist.md](information-checklist.md) の **P0 → P1 → P2** に従う。

| 優先 | 典型項目 | 他章への影響 |
| --- | --- | --- |
| P0 | 対象システム・スコープ内外・テストフェーズの切り方 | 全体の骨格 |
| P1 | 品質方針（数値目標の有無）、観点の扱い、リリース判定、体制の記載方針 | §3, §4, §5 |
| P2 | スケジュール目標、環境 URL、顧客提出物、詳細リスク | §6, §8, 付録 |

### 1回の質問は1〜2個

悪い例: 15項目を一度に列挙して回答を求める  
良い例: 「Phase1 の対象はデザインツールのみで合っていますか？ それとも EC 購入フローも同時に含めますか？」

### 選択肢を出すとき

`決定が必要な項目.md` と同様、**案A / 案B + メリット・デメリット**を短く示し、ユーザーの決定をそのまま計画書に転記する。

### 更新サイクル

```
未決の発見 → 確認事項一覧に追記 → ユーザー決定 → 計画書反映 → バージョンアップ
```

新たな未決が出たら **計画書を古い決定で上書きしない**。更新履歴に「〇〇は未決のため【要確認】のまま」と書いてよい。

## 全文出力の確認（必須）

- Phase B/C 前: 「§2 と §3 のドラフトを出力してよいですか？」
- 「棚卸しだけ」「何が必要か教えて」→ Phase A のみ
- 追加情報待ち → ドラフトしない

## 品質ルール

- **日本語**
- **トークン節約**: 既定は Phase A のみ
- **トレーサビリティ**: 計画書の断定文には可能なら根拠（要件 CSV 行、議事録、ユーザー発言）を社内メモで保持
- **他ドキュメントとの整合**: 観点・フェーズ名は `観点一覧_共通.md` / `01_機能×観点カバレッジ表.md` と矛盾させない。矛盾があればユーザーに確認
- **ISO 29119**: 本スキルの章立ては Test Plan（§6.2 相当）の実務写像。規格用語を前面に出す必要はない
