# テストケース生成

依頼を受けたら、**リポジトリ内ドキュメント・仕様・コードを実際に参照**し、まず**生成可否の判断結果**を返す。仕様にない挙動を推測で手順化しない。**ケース全文はユーザーが明示的に了承するまで出力しない**（トークン節約）。

注意: Skills 作成途中のため、本 Skill に順守して出力すること。チャットの推測だけでケースを書かない。ドキュメントに記載された内容のみ根拠にできる。

## テストケースの粒度（L1〜L4）

| レベル | 名称 | 1件の内容 | 必要な根拠ソース（例） |
| --- | --- | --- | --- |
| **L1** | シナリオ | 業務フロー単位の検証観点（1〜3文） | 受入テスト観点、UAT 設計、テスト計画の重点領域 |
| **L2** | 機能×観点 | 機能ID × TP-xx の検証項目（骨格） | 01a/01b/01c、観点一覧_共通、02_観点カバレッジ評価表の「無」 |
| **L3** | ケースブロック | `★EC>…` 形式のケース名＋概要＋前提 | 結合テスト設計書、action-spec、画面遷移、既存ケースの命名規則 |
| **L4** | 手順詳細 | No / 操作 / 期待する動作 / 観点 / 正常・準正常・異常 | action-spec、ec_api_detail、OpenAPI、既存 26/28/25/27 の表形式 |

**原則**: 上位レベルは下位より少ない根拠で生成可。L4 は **画面パス・API・バリデーション・期待レスポンス** が仕様に明示されている領域に限定する。

## 作業手順

### Phase A: 調査と生成可否判断（既定・第1レスポンス）

**この Phase のみでレスポンスを終える。** 長大なケース表・全件リストは出さない。

1. **スコープを確定** — 対象（EC / Creator / 管理画面 / 単体 / 総合 / UAT）、フェーズ、機能ID または画面。
2. **既存ドキュメントを読む** — 下記「参照優先順位」および [kjdd-sources.md](kjdd-sources.md)。
3. **既存ケースとの重複を確認** — 28（EC正）/ 26 / 25 / 27 / 20_単体 / Issues の検出パターン。
4. **レベル別に ○／△／× を判定** — 下記テンプレートに沿って返す。
5. **欠損情報を要請** — × や L4 の △ について、用途・形式を列挙。
6. **全文出力の確認** — 了承があるまで Phase B に進まない。

### Phase B: ケース生成（ユーザー了承後のみ）

ユーザーが「生成して」「L3 だけ」「EC-005 の穴埋め」等と**明示**した場合のみ実施。

1. **出力レベル・範囲**を依頼どおりに限定（全レベル一括は避ける）。
2. **既存の記載形式に厳密に合わせる** — KJDD 結合は `26_EC画面_結合テストケース詳細.md` の方針・表構造を正とする（28 は別ソース正だが表形式は同一系）。
3. **新規ケースには根拠列を付ける** — 仕様パス・既存ケース No・機能要件 No。
4. **保存先**（ユーザー指定がなければ KJDD 既定）:
   - 結合 L4 追記: 対象に応じ `26_*` / `25_*` / `27_*` または新規 md
   - L2 骨格: `21_結合テスト項目表.md` への追記案
   - L1: `client-kingjim-pm-cursor/docs/受入テスト観点.md` 形式または別 md
5. **索引 md のみ**を `20_作成資料/テスト/【テスト項目表】/` に置く場合は長文を載せない。

## 生成可否判断（Phase A の既定出力）

第1レスポンスは**必ずこの形式のみ**。

```markdown
# テストケース生成 — 生成可否判断

## 依頼スコープ
（対象システム・フェーズ・機能・希望レベル）

## 参照した情報
（パス・ファイル名。ユーザー提供があれば明記）

## レベル別の生成可否

| レベル | 判定 | 根拠・現状 | 全文生成に必要な追加情報 |
| --- | --- | --- | --- |
| L1 シナリオ | ○／△／× | | |
| L2 機能×観点 | ○／△／× | | |
| L3 ケースブロック | ○／△／× | | |
| L4 手順詳細 | ○／△／× | | |

**判定の意味**
- **○ 生成可**: 根拠十分。推測なしで書ける
- **△ 一部可**: 骨格・一部手順は可。バリデーション詳細・テストデータ等が欠ける
- **× 不可**: 仕様根拠なし。要請またはスコープ縮小が必要

## 既存ケースとの関係
（新規 / 追補 / 重複注意 のいずれかと件数目安）

## 追加でいただきたい情報（△・× を集約）
（各項目に「用途」「形式の例」）

## 次のアクション
ケース全文の出力はご確認後に行います。
**どのレベル・範囲を生成してよいですか？** 不要なレベルがあればお知らせください。
```

### 判断ルール

- **推測で ○ にしない。** 「根拠・現状」にソースを1行で示す。
- **既存 700 件超の EC 結合** — 新規生成より **ギャップ追補** を優先。02_評価表の「無」「要確認」を先に列挙。
- **21_結合テスト項目表・22_総合テスト項目表** — 中身が空のため、L2/L3 の**新規整備**は ○ だが L4 は領域次第。
- **UAT L4** — `14_UATテスト設計書` はシナリオを本リポジトリで管理しない方針。**L1 のみ ○**（受入テスト観点あり）。
- Phase A でケース表の先行出力をしない。

## 全文出力の確認（必須）

- Phase B 前に必ず確認。「上記の判断をもとに、L3 の EC-005 のみ生成してよいですか？」
- 「判断だけ」「可否だけ」→ Phase B しない
- 追加情報待ち → Phase B しない

## KJDD 結合テスト L4 の書式（Phase B）

[26_EC画面_結合テストケース詳細](kjdd-sources.md) の方針に従う。

**ケースブロック見出し**

```markdown
### テストケース名：★{大分類}>{中分類}>{小分類}>{操作名}
```

**手順表**

| No | 操作（Action） | 期待する動作 | 観点 | 正常系 | 準正常系 | 異常系 |
| --- | --- | --- | --- | --- | --- | --- |

**必須方針（EC・管理画面共通）**

- ケース独立性（手順1で状態まで到達）
- 直接 URL と正常系ルートの両方（該当画面）
- 準正常後の正常復帰
- 決済は GMO FAQ（D00867, D00861）参照を注記
- API パスは action-spec / OpenAPI と突合。未記載は `【要仕様確認】` とし推測しない

詳細テンプレートは [templates.md](templates.md)。

## 参照優先順位

1. **既存テストケース** — 28（EC観点正）> 26 > 25 > 27 > クリエーター向け 21
2. **カバレッジ** — 01a/01b/01c、02_観点カバレッジ評価表、EC_結合テストケース_観点カバレッジ集計
3. **設計** — 10〜14_テスト設計書、観点一覧_共通
4. **仕様** — `client-kingjim-system-design/`（action-spec-generation、ec_api_detail、admin_detail、function_requirements.csv）
5. **テストデータ** — `テストデータ投入ガイド.md`
6. **コード** — 単体 L4・API 契約の補強のみ（画面 L4 の主根拠にしない）

## 判断材料不足時

要請文の型:

> 「{機能} の L4 手順を確定するため、以下が必要です。ご提供いただけますか？
> - 必要データ: （例: POST /api/orders のエラーコード一覧、バリデーション文言）
> - 用途: 準正常系 No.3〜5 の期待結果
> - 形式: OpenAPI 抜粋、action-spec md、スクショ、既存ケース Excel の該当行
> 不要であれば L2 骨格のみ生成します。」

### 典型的にユーザー提供が必要なもの（KJDD）

| 項目 | 影響レベル | 省略時 |
| --- | --- | --- |
| 環境 URL・ログインアカウント | L4 | パスのみ記載、URL は `（環境により異なる）` |
| GMO / 3DS テストカード・サンドボックス手順 | L4（決済） | L3 まで。L4 は正常系のみ |
| バリデーション境界値（文字数・形式） | L4 | L3 + `【要仕様確認】` 行 |
| 性能・負荷の閾値 | L1/L2 | 総合テストは骨格のみ |
| 管理画面 API の所在（Phase2） | 単体 L4 | ec-api のみ生成可と明記 |
| 新機能の action-spec 未作成 | L3 以下 | × または L1 のみ |

## 品質ルール

- **日本語**
- **トークン節約**: 既定 Phase A のみ
- **重複生成禁止**: 28/25/27 に同等ケースがある場合は「追補不要」と報告
- Phase B セルフレビュー: 観点ID の正規化（TP-xx）、正常/準正常/異常の排他、根拠パスの整合
