# 機能×観点カバレッジ表（対話ドリブン）

依頼を受けたら、**マトリクスを一括で埋めない**。リポジトリ・既存資料を読み、**何が分かっていて何が未決か**を整理し、ユーザーと**壁打ち**しながらカバレッジ表を育てる。**全文・全セル出力はユーザーが明示的に了承するまで行わない**（トークン節約・誤合意防止）。

本 Skill は**作成で終わらない**。更新履歴・関連ドキュメント同期・(n) 再集計を**継続メンテナンス**の前提で運用する。

## プロジェクトプロファイル（Phase 0 必須）

[_shared/profile-resolution.md](../_shared/profile-resolution.md) に従い、**保存先・参照先は profile から解決**する。

| profile キー | 用途 |
| --- | --- |
| `paths.coverage_index` | L1 索引 |
| `paths.coverage_estimate` | L2 規模見積 |
| `paths.viewpoint_common` | L3 観点定義 |
| `paths.coverage_eval` | L4 評価表 |
| `paths.coverage_matrix_l3_prefix` | L3 系統別（01a/b/c）のディレクトリ接頭 |
| `paths.skills_build_dir` | Skill 検証用ドラフト（本番と分離） |
| `sources.*` | 要件・ケース正ソース |
| `conventions.*` | 機能ID・組合せ方針・重点領域 |

KJDD 向け補足参照: [kjdd-sources.md](kjdd-sources.md)（profile と矛盾する場合は profile / ユーザー合意を優先）。

## ユーザーとの進め方（Phase 名対応表）

Phase は**エージェント内部の作業名**。ユーザーには次の言い方で説明する。

| 内部名 | ユーザー向け | エージェントが出すもの | ユーザーがすること |
| --- | --- | --- | --- |
| Phase 0 | （表に出さない） | なし | なし — リポジトリを読むだけ |
| **Phase A** | **ステップ1: 作成可否の報告** | 🟢🟡🔴 の表・質問 1〜2 個 | 質問に答える。**まだ md は出ない** |
| **Phase B** | **ステップ2: ドラフト提示** | 合意した範囲の md **本文**（チャット） | 内容を確認し OK / 修正指示 |
| **Phase C** | **ステップ3: ファイル保存** | 合意済みドラフトを**ファイルに書く** | 保存後、本番と diff してフィードバック |
| Phase D | 更新・メンテ | 差分更新 | 同上 |

**Phase B = あなたへの合意取得のステップ。** 「この範囲のドラフトを出してよいか」を先に聞き、OK 後に本文を見せる。Phase C = OK した内容をリポジトリに保存する。

### 合意の取り方（何に OK をもらうか）

合意は**2段階**で取る。混同しない。

1. **範囲の合意**（Phase B に入る前）  
   例: 「`観点一覧_共通.md` と `01_機能×観点カバレッジ表.md`（索引）を、Skills構築用フォルダ向けに作成してよいですか？」  
   → ユーザーが OK / スコープ修正

2. **内容の合意**（Phase B のドラフト提示後）  
   例: 「このドラフトでファイル保存（Phase C）してよいですか？」  
   → ユーザーが OK / 修正指示

**一括出力**: 無駄な出力を抑えるため、**デフォルトは 1 ファイル（または 1 セクション）ずつ**。ユーザーが「索引＋観点一覧を**まとめて**ドラフト出力して」と**明示**した場合は、Phase B の範囲を広げてよい。それでも Phase B（提示）→ 内容合意 → Phase C（保存）の順は守る。

### 本番ドキュメントとの関係

| 用途 | 扱い |
| --- | --- |
| **品質比較** | 本番 `【テスト計画】/01_*` を**読んで diff する基準**として使う |
| **作成の入力** | 要件 CSV・ケース 28/25/27・設計書・QA 見解など**根拠ソース**から組み立てる |
| **禁止** | 本番 md の**写経・コピペ**を Phase B/C の成果物とする（Skill 検証にならない） |

Skills 構築用フォルダの出力は、Phase C 保存後に本番と比較し、ユーザーが Skill 改善のフィードバックを行う想定。

### エージェントの禁止事項（合意フロー）

- Phase A で「Phase B に必要な条件」に**写経**を載せない
- ユーザー向け質問に **Phase B / Phase C という語 alone を使わない** — 「ドラフト提示」「ファイル保存」と言う
- ユーザーが OK していない範囲の md を Phase C しない
- チャットに長大マトリクスを Phase A で出さない

## 成果物の4層（L1〜L4）

対話で**この順**に育てる。上位が未合意のまま下位に進まない。

| 層 | ドキュメント（profile `paths`） | 目的 | テスト計画書との関係 |
| --- | --- | --- | --- |
| **L1** | `coverage_index`（索引） | 目的・機能一覧・C/I（高/中/低）・系統・フェーズ概要 | §2 スコープ・§3 方針の入力 |
| **L2** | `coverage_estimate` | パラメータモデル・100%見積・2-way/採用見込・削減方針 | **§3 品質方針に反映必須**（合意後） |
| **L3** | `viewpoint_common` + `coverage_matrix_l3_prefix` 配下 01a/b/c | TP 定義・◎○△− マトリクス | §3 観点・設計書への入力 |
| **L4** | `coverage_eval` + 項目表 | ケース有無・(n) 実績・見積との差分 | 実行・リリース判定 |

**複雑度・重要度**

- **L1 表向き**: 高 / 中 / 低（ステークホルダー向け）
- **L2 内部**: 複雑度 C・重要度 I を **各 1〜5**（`03` に記載）
- **組合せ方針（profile `conventions.combination_policy` 参照。未設定時は 2-way 基本）**:
  - **ベース**: **2-way のみ**
  - **3-way**: 複雑度・重要度が高い（**R1**: C×I ≧ 20、または L1 で高/高）機能で**検討**。採用 triple は L2 機能別詳細に列挙
  - **100% 全組合せ**: 原則しない（論理最大は説明用）
- **リスクティア**: C×I → R1〜R4 → 上記方針の適用深度

**L2 見積の出力列（機能サマリ）**

| 列 | 意味 |
| --- | --- |
| 論理最大 | 全組合せを naive に数えた上限（削減の根拠） |
| 2-way 見積 | ペアワイズ等の covering array 見込 |
| 採用方針 | **2-way 基本** / 2-way + **3-way 検討**（R1・高/高） / 100% は原則不可 |
| 採用見込ケース | 方針反映後の結合テスト目安 |
| 実 (n) | L4。未作成時は空 |

**(n)**: L4 で `count_viewpoints_*.py` 集計。L2 の採用見込との差分をレビューする。

## このスキルでやること / やらないこと

**やる**

- カバレッジ表群に必要な**情報項目の棚卸し**と優先度付け
- 既存資料・テストケースから**確定事項の抽出**（推測は `【要確認】` と明記）
- **1回のレスポンスで質問は1〜2個**に絞った壁打ち
- 合意済み範囲のみ段階的にドラフト化（系統単位・機能ID単位・観点単位）
- **3系統＋索引＋観点定義**の双方向同期（[template.md](template.md) 参照）
- `02_観点カバレッジ評価表` との**整合チェック**（◎○△ 変更時は評価表更新を促す）
- 条件が固まるたびに**バージョン・更新履歴**を追記して改訂
- **メンテナンスサイクル**（ケース追加・機能分割・別ソース正の切替）の記録

**やらない（別スキルへ）**

- テスト計画書本体 → [test-plan-creation](../test-plan-creation/SKILL.md)
- テストケース・手順詳細の生成 → [test-case-generation](../test-case-generation/SKILL.md)
- テスト完了レポート → [test-completion-report](../test-completion-report/SKILL.md)
- 観点の◎○△− の**最終ビジネス判断**（ファシリテーションと選択肢提示はする）

## 作業フェーズ

### Phase 0: コンテキスト把握（初回・更新時）

ファイルを書き換える前に実施。

1. **既存カバレッジ表**があれば読む（profile の L1〜L4 パス、バージョン・更新履歴）
2. **テスト計画・設計**の入口（`paths.test_plan`、10〜14 設計書）
3. **テストケース正ソース**の特定（`sources.*`。[kjdd-sources.md](kjdd-sources.md) は KJDD 補足）
4. **機能要件**（`sources.requirements` 等）で機能ID の根拠を確認
5. **依頼の種類**を判定: 新規作成 / 部分更新 / メンテ（(n) 再集計・機能追加・観点定義変更）/ 評価表同期のみ

### Phase A: 作成可否判断・情報棚卸し（既定・第1レスポンス）

**この Phase のみでレスポンスを終える。** マトリクス全文・全機能×全観点の表は出さない。

1. [information-checklist.md](information-checklist.md) の項目を棚卸しし、ドキュメントごとに **作成可否シグナル**（🟢🟡🔴）を付ける
2. リポジトリから**根拠パス**を1行ずつ付ける（推測で 🟢 にしない）
3. **次に聞くべき質問を1〜2個**に絞る（🟡 の条件解消、🔴 の P0 補完を優先）
4. ステップ2（ドラフト提示）に進めるか示し、**範囲合意**を求める

**第1レスポンスは必ずこの形式**

```markdown
# 機能×観点カバレッジ表 — 作成可否判断

## 依頼の理解
（新規 / 改訂 / メンテ / 対象系統・機能ID）

## 参照した情報
（パス・ファイル名）

## ドキュメント別の作成可否

| ドキュメント | 作成可否 | 根拠・現状 | 着手前に足りないもの |
| --- | --- | --- | --- |
| L1 01 索引 | 🟢／🟡／🔴 | | |
| L2 03 規模見積 | | | |
| L3 観点一覧_共通 | | | |
| L3 01a / 01b / 01c | | | |
| L4 02 評価表 | | | |

**作成可否シグナル**

| シグナル | 意味 | 次のステップ |
| --- | --- | --- |
| 🟢 **作成可** | Skill に沿って作成可能。**期待した品質の出力**が得られる根拠が揃っている | **範囲の合意**後にステップ2（ドラフト提示）可 |
| 🟡 **条件付き作成可** | 作成可能だが、**未決が残ると精度低下**または**既知ギャップ**が残る | 質問 1〜2 個で未決を解消してから範囲合意 |
| 🔴 **作成不可** | 前提・情報が不足し、無理に作ると**期待品質を満たせない** | ステップ2 禁止。情報取得・合意を先に |

**判定ルール（推測で 🟢 にしない）**

- 🟢: 当該 md の P0（系統・機能ID・観点セット・正ソース）が**根拠ソース**から確定できる
- 🟡: 骨格は書けるが、(n) の正ソース未確認・他表との不整合・◎○△ の未決セルあり等。**「着手前に足りないもの」列に具体項目を書く**
- 🔴: 機能ID 規則なし・観点未定・ケース正ソース不明・スコープ未合意など P0 欠落
- 出力先にファイルが無いこと自体は 🔴 理由にならない
- **本番 md が存在することは 🟢 理由にならない**（比較基準であり、入力の代わりにしない）

**配置状況（任意・補助）**: 出力先に md が未配置なら「未配置」と1語添えてよい。作成可否とは別軸

## 系統・スコープの整理
（3系統のうち対象、Phase、機能ID プレフィックス方針）

## いま優先して決めたいこと（P0）
（未決のうち、他の表の前提になるものを最大3項目）

## 今回の質問（1〜2個に限定）
1. …
2. …

## 次のアクション
ステップ2（ドラフト提示）は、上記への回答と**範囲の合意**後に行います。
**例: 「`観点一覧_共通` と索引だけ、Skills構築用にドラフト出して」** のように、対象ファイルを指定してください。
```

### ステップ2: ドラフト提示（内部 Phase B）

ユーザーがスコープを**明示**し、**範囲の合意**が取れた場合のみ。例: 「観点一覧と索引をドラフト出して」「01a の EC-004 行だけ」

**ルール**

- **合意済み**のセルのみ ◎○△− を断定。未決は `【要確認】`
- 推測で重要度・複雑度・(n) を埋めない（集計スクリプト実行結果またはユーザー合意が必要）
- **依頼範囲**に限定（ユーザーが「まとめて」と明示した場合は複数ファイル可）
- ドラフト末尾に **未決リスト** と **同期が必要な他ファイル** を付ける
- 提示後: **「この内容でファイル保存してよいですか？」**（内容の合意）

### ステップ3: ファイル保存（内部 Phase C）

**内容の合意**後のみ。

1. 対象 md を**差分更新**（全置換しない）
2. **更新履歴**にバージョン・日付・変更概要。ヘッダに **作成 Skill 版**（qa-skills.lock + metadata.version）を追記
3. **連動更新**（該当時）:
   - 機能追加・分割 → 01 索引の機能一覧、該当 01a/b/c、02 評価表
   - 観点定義変更 → `観点一覧_共通` → 全マトリクスの備考・列見出し整合
   - ◎○△ 変更 → 02 で該当行の「有/無/要確認」見直しを促す
   - (n) 更新 → 正ソースのケース反映後、`scripts/count_viewpoints_*.py` 再実行を記録
4. リンクは**実在ファイル**にのみ張る

### Phase D: 継続メンテナンス（作成後も同 Skill）

カバレッジ表は**生きたドキュメント**。以下のトリガーで Phase 0 → A（簡易）→ B/C を繰り返す。

| トリガー | 典型アクション |
| --- | --- |
| テストケース追加・観点タグ付与 | (n) 再集計、02 評価更新 |
| 機能要件追加・分割 | 機能ID 行追加、索引同期 |
| 別ソース正の切替（例: 26→28） | 凡例・集計元・(n) 一括更新 |
| 実装方針変更（例: モバイル範囲） | TP-xx 定義、◎○△−、QA見解 |
| 擦り合わせ・QAレビュー | 備考・セルフレビュー節追記 |

**メンテ時の最小確認**: 索引 ↔ 01a/b/c ↔ 観点一覧_共通 ↔ 02 ↔ ケース正ソース の**5点整合**。

## 壁打ちの進め方

### 質問の優先順位

[information-checklist.md](information-checklist.md) の **P0 → P1 → P2** に従う。

| 優先 | 典型項目 | 層 |
| --- | --- | --- |
| P0 | 系統分割・機能ID 粒度・観点セット | L1 |
| P0 | 組合せ方針（**2-way 基本 + 高リスクで 3-way 検討**）・R1 機能の triple 採否 | L2 → 00 §3 |
| P1 | ◎○△−、(n) 正ソース | L3 / L4 |

### 1回の質問は1〜2個

悪い例: 全機能×全15観点の ◎○△ を一度に決めさせる  
良い例: 「EC-005 の TP-07 は − で合意済みですが、EC-007 の注文履歴 DL は ○ でよいですか？」

### 選択肢を出すとき

**案A / 案B + メリット・デメリット**を短く示し、ユーザーの決定をそのまま表に転記する。

### 更新サイクル

```
未決の発見 → Phase A で確認 → ユーザー決定 → 部分ドラフト → ファイル反映 → 関連表同期 → バージョンアップ
```

## 全文出力の確認（必須）

- ステップ2 前: **範囲の合意** — 「`観点一覧_共通` をドラフト出力してよいですか？」
- ステップ3 前: **内容の合意** — 「このドラフトで Skills構築用フォルダに保存してよいですか？」
- 「可否だけ」「棚卸しだけ」→ ステップ1 のみ
- 追加情報待ち → ドラフトしない

## 品質ルール

- **日本語**
- **トークン節約**: 既定は Phase A のみ
- **トレーサビリティ**: ◎○△− と (n) には根拠（ケース No、ユーザー合意、仕様パス）を社内メモで保持
- **他ドキュメントとの整合**: フェーズ名・機能ID は `00_テスト計画書` / `test-plan-creation` と矛盾させない
- **(n) の扱い**: 集計スクリプト出力またはユーザー提供値のみ。手計算の推測値は `【要集計】`
- **セルフレビュー**: 大きな改訂時は QA見解節（01a 型）を検討。ユーザーが不要と言えば省略
