# 依頼内容から標準観点へ反映する

## 目的

ユーザーがプロンプトで依頼した観点を、**正規の観点一覧**（`viewpoints/`）と **`標準観点表-統合版.md`** の両方に一貫して追加する。日本語は読み手が迷わない表現にする。既存と**同等**の観点があれば二重登録しない。境界なら**ユーザーに確認**してから進める。

## 前提パス

- ワークスペースが親リポジトリのとき: `standard-viewpoint-table/` 配下を正とする。
- 機能とファイルの対応: [../standard-viewpoints-qa/reference.md](../standard-viewpoints-qa/reference.md) の「機能別索引」。

## 作業フロー（必須順）

### 1. 依頼の解釈

- **何を防ぎたいか**（失敗モード・再現条件・UI/API のどこか）を1〜2文で要約する。
- **対象機能カテゴリ**（例: 登録・編集、デザインツール、情報変更）と **プラットフォーム**（共通 / web / アプリ）を決める。依頼に明示がなければ、バグの発生箇所から推定し、**複数フォルダにまたがる場合は両方**を候補にする。
- 索引で **実在する** `共通.md` / `web.md` / `アプリ.md` のみを対象にする（`-` の列は作らない）。

### 2. 重複チェック（追加前に必須）

次を **Grep または Read** で洗う（キーワードは依頼文から抽出: 例「スライダー」「自動保存」「連打」「デバウンス」）。

| 検索対象 | 目的 |
| --- | --- |
| 該当しそうな `viewpoints/**/*.md` | 同じテーマの行がないか |
| `標準観点表-統合版.md` | 統合表側の重複 |
| 対象 `web.md` / `アプリ.md` 内の **「共通観点（00-共通から移植）」** ブロック | 00-共通相当が既に移植されていないか |

**同等とみなす基準**（いずれか該当なら新規行を増やさない）:

- 「テスト項目（観点）」が同義・表記ゆれのみ違う。
- 「確認内容・期待値」が、依頼のリスクを**すでにカバー**している（例: 「高頻度操作時の自動保存」が既にあり、依頼がスライダー連続操作のみに限定される場合など）。

**判断が割れるとき**（必ずユーザーに止まる）:

- 既存行は狭いが依頼は広い／その逆。
- 新規にすると表が冗長だが、**キーワードが違う**ため検索しづらい、など。

ユーザーへの聞き方の例:

- 既存行を引用（ファイル名・テスト項目・確認内容の要約）。
- 追加案を1行で提示。
- 「同等で追加不要」「既存の確認内容を拡張」「別観点として追加」のどれにするかを選択してもらう。

### 3. 追加する場合の編集ルール

**`viewpoints/{機能}/{共通|web|アプリ}.md`**

- 観点一覧は **4列**: 機能 or 表示 / テスト観点カテゴリ / テスト項目（観点）/ 確認内容・期待値。
- 新規行は **機能固有の「観点一覧」表**に入れる。`### 共通観点（00-共通から移植）` ブロックは**依頼が00-共通レベルの横断要件のときのみ**検討し、原則は触らない（[../standard-viewpoints-qa/SKILL.md](../standard-viewpoints-qa/SKILL.md) のスタイルルールに従う）。
- **テスト項目**は短く、**確認内容**に具体条件（操作手順・境界・期待する保存/表示）を書く。略語は初出で補う。
- ファイル末尾の **編集履歴** に1行追加する（日付はユーザーの「今日」または依頼文脈。不明なら作業日を `YYYY-MM-DD` で明示）。[../standard-viewpoints-qa/examples.md](../standard-viewpoints-qa/examples.md) の「反映時」形式。

**`標準観点表-統合版.md`**

- 該当 **機能ID・機能カテゴリ・web or アプリ** は索引表と既存行を合わせる（例: 登録・編集 Web なら `4` / `登録・編集` / `web`）。
- 統合表は **7列**（機能ID / 機能カテゴリ / web or アプリ / 機能 or 表示 / テスト観点カテゴリ / テスト項目 / 確認内容・期待値）。`viewpoints/` に追加した行と **同一内容**の行を入れる。
- 挿入位置は **同じ機能IDのブロック内**で、意味が近い行の**直後**（なければ該当ブロックの末尾）に置く。他機能の並びは崩さない。

**テストレベル切り分け**

- 単体で主に担保／結合必須が分かれる内容なら、該当ファイルに `### テストレベル（単体／結合以降）` があるか確認し、必要ならそのサブ表に追記する。指針は `docs/テストレベル指針（単体と結合）.md`。

### 4. 完了時の出力

ユーザーに次を簡潔に返す:

- 追加しなかった場合: **どの既存観点がカバーするか**（ファイルとテスト項目名）。
- 追加した場合: **変更したファイル一覧**、追加大意、編集履歴に書いた学び元（依頼文から分かる範囲で）。

## 例（依頼の扱い）

**依頼**: 「スライダーを素早く操作すると自動保存されないバグ。事前検出できるよう観点を更新」

1. 索引: デザインツール Web（22）、情報変更、登録・編集など候補を grep（「自動保存」「スライダー」「デバウンス」「高頻度」）。
2. `viewpoints/22-デザインツール/web.md` に既に「自動保存・高頻度操作」系があれば、**同等か**を判断。境界ならユーザーに「既存行の拡張 vs スライダー専用の1行」を確認。
3. 追加するなら `22-デザインツール/web.md` の観点表 ＋ `標準観点表-統合版.md` の機能ID 22 付近に同内容の7列行を追加し、両方の編集履歴（viewpoints 側は必須）を更新。
