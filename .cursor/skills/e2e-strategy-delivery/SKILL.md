# E2E 戦略とデリバリー（計画書・設計書ドリブン）

## このスキルでやること / やらないこと

**やる**

- リポジトリを読み、**どこがビジネスクリティカルか**をユーザーと擦り合わせる
- **画面遷移・状態**をリポジトリ内の **Mermaid ドキュメント**で可視化し、ナビゲーション変更時は **図を先に更新**する運用を計画書／設計書に紐づける（詳細は下記「画面遷移図」）
- **E2E自動テスト計画書**（スコープ・シナリオ・優先度・合意）をドラフト→レビュー→改訂のループで固める
- **E2E自動テスト設計書**（ツール、構成、CI、保守方針、**POM 規約**）を壁打ちしながら作り、必要なら差し替える
- テストコードは **Page Object Model（POM）** を既定とする（画面＝Page / Screen、操作＝メソッド、セレクタは Page に閉じる）。スペックはシナリオの Given-When-Then のみに近づける
- **Mermaid 上のパス**からシナリオを切り出し、計画書のシナリオ ID・P0/P1 と突合してから実装する（下記「図からシナリオへ」）
- 実装は「**継続的に緑を保てる最小セット**」から始め、CI に載せる

**やらない（別スキル・別タスク）**

- プロダクトの要件定義そのものの最終決定（合意形成のファシリテーションはする）
- ツールの詳細セットアップ手順の網羅 → モバイルで Appium 具体手順は [appium-e2e-setup](../appium-e2e-setup/SKILL.md) を読む

## 優先順位（必ずこの順）

1. **重要ロジックを E2E（＋CI/CD）で継続保証できる状態**にする（壊れたら止まる、が理想）
2. **実装・メンテの総工数を最小**にする（フレーク対策・セレクタ方針・データ準備まで設計書に書く）

## アンチパターン（明示的に避ける）

- **なんでも E2E**：画面遷移の網羅、細かい UI のみ、API/単体で十分な箇所まで E2E に寄せない
- **計画・設計なしの実装**：先にツールを決め打ちで入れる（既存スタックとの整合を後付けにしない）
- **CI に載らない E2E**：ローカル専用の大量シナリオは優先度を下げるか削る
- **スペックにセレクタだらけ**：POM を迂回して `*.spec.ts` に locator をべた書きしない（保守不能になる）
- **図なきシナリオ増殖**：計画書にないパスを、図も更新せずテストだけ増やさない

## Page Object Model（POM）— 既定の実装方針

- **Screen / Page クラス（またはモジュール）** が **その画面のセレクタと操作**を保持する。スペックは「どの Page をどう組み合わせるか」とアサーション中心に書く。
- **同一画面の複数状態**（例: ログイン前タブ／モーダル表示中）は、サブクラス分け・ファクトリ・明示メソッドのいずれかで Page 側に閉じ、スペックは状態名で読めるようにする。
- **共通部品**（タブバー、ヘッダ、トースト）は `components/` 等に切り出し、複数 Page から合成する。
- 設計書に **Page の置き場・命名（`pages/` vs `screenObjects/`）・継承の可否** を1回書き、既存 E2E と揃える。

## 画面遷移図（Mermaid）— リポジトリ内の正

- **目的:** アプリ内の**到達可能な画面と遷移**を一枚以上の Mermaid で共有し、E2E・手動・PM が同じ地図を参照する。
- **置き場の例:** `docs/e2e/e2e-screen-flows.md`（プロジェクトに内包。ナビ変更の PR では **図の更新を同一 PR またはフォローイシュー必須**と設計書に書く）。
- **粒度:** 計画書の P0 に対応する**クリティカルパス**は必ず図に載せる。全画面網羅は不要（ピラミッドと計画書の対象外と整合）。
- **記法:** `flowchart` / `stateDiagram-v2` などチームで読みやすいものを選び、**ノード ID は画面・状態の安定した略名**にする（テストコードの Page 名と対応付け可能にするとよい）。

## 図から E2E シナリオへ — 作業の流れ

1. **図上のパスを列挙** — 起点（例: コールドスタート）から、計画書で P0 の終状態（例: 注文確定画面）に至る**辺の列**を1本ずつ取り出す。分岐ごとに別パス＝別シナリオ候補。
2. **各パスを表にする** — 列: シナリオID（計画書の ID または仮 ID）、Given（前提データ・ログイン状態）、When（辺＝Page メソッドの列）、Then（到達ノード＋観測可能な期待）。
3. **計画書と突合** — 既存のシナリオ表にマップし、足りなければ計画書を先に改訂（合意ゲート）。
4. **POM に落とす** — 各ノード → Page、各辺 → Page のメソッド。不足メソッドは図を見ながら追加。
5. **スペック化** — `*.spec.ts` は上記表の1行に近い構造にし、フレークしやすい待機は設計書の方針に従い Page 内に閉じる。

**出力物の対応関係:** Mermaid（遷移の真実）→ シナリオ表（計画書）→ Page 群（設計書の POM 節）→ `*.spec.ts`（CI）。

## フェーズ 0 — プロジェクト把握（読み取り中心）

ファイルを変える前に、会話またはメモで次を埋める。

- アプリ種別（Web / RN・Expo / ネイティブ / ハイブリッド）、主要ユーザーフロー
- 認証・決済・在庫・権限など **壊れると致命傷**な領域
- 既存テスト（単体・結合・契約・既存 E2E）と CI の有無
- `package.json` / CI 設定 / 既存 E2E 設定（Playwright, Detox, Maestro, WDIO 等）の有無

**出力:** 「クリティカルパス一覧（仮）」と「E2E にしない方がよい領域（仮）」

## フェーズ 1 — E2E自動テスト計画書（合意まで繰り返し）

1. [templates.md](templates.md) の **計画書テンプレ**でドラフトを書く
2. ユーザーと **スコープ・優先度・対象外**を一文ずつ合意（曖昧なら質問を 1 つに絞る）
3. 実装やツール変更のたびに **計画書を更新**できる旨を冒頭に書いておく

**ゲート:** 計画書の「合意欄」が空のまま本番向けシナリオを増やさない

## フェーズ 2 — ツール選定と E2E自動テスト設計書

1. スタック適合（言語・既存ライブラリ・チーム習熟）と **CI で回せるか**で候補を 2〜3 に絞る
2. [templates.md](templates.md) の **設計書テンプレ**で比較表・採用理由・リスクを書く
3. **壁打ち OK・追記削除自由**。方針転換したら設計書に「変更理由」と日付を残す

**モバイルで Appium 系に寄った場合:** 依存追加や `doctor` 運用は `appium-e2e-setup` のゲート（承認前は lockfile を触らない等）に従う

## フェーズ 3 — 実装と CI（最小から）

- **Mermaid のクリティカルパス**と計画書 P0 を突合済みであること（フェーズ1・2の後、実装直前でもよい）
- **POM** に沿って Page を用意し、**スモーク相当の本番クリティカルパス**からテストを書き、**main/PR で実行**できるようにする
- フレーク・テストデータ・環境変数は設計書に「再現手順」まで書く
- シナリオ追加は計画書の優先度に照らす（計画外は「次のイテレーション」扱い）。追加時は **Mermaid を先に更新**

