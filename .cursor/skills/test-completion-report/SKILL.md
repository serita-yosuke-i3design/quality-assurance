# テスト完了レポート作成

依頼を受けたら、**リポジトリ・phennec・ユーザー提供データを実際に参照**し、まず**出力可否の判断結果**を返す。推測で数値を埋めない。**レポート全文はユーザーが明示的に了承するまで出力しない**（トークン節約）。

注意点: 現時点ではSkillsの内容を作成している途中のため、このSkillsに順守して出力することとし、チャット内容などから推測して出力しないこと。参照可能情報として、ドキュメントに記載されている内容は考慮して良い。

## 規格との対応（ISO/IEC/IEEE 29119-3 §7.4）

本スキルの出力骨組みは、規格の Test Completion Report を次のように写像する。

| 規格（§7.4） | 本スキルの見出し | 備考 |
| --- | --- | --- |
| 7.4.1 Overview | テスト概要と実施体制（冒頭）＋レポート情報 | 対象・期間・規模をコンパクトに。結論は §7.4.4 へ |
| 7.4.2 Summary of testing performed | テスト概要と実施体制／実施テスト一覧 | 既存計画・設計に準拠 |
| 7.4.3 Deviations from planned testing | 計画からの変更（任意） | 差分があるときのみ |
| 7.4.4 Test completion evaluation | 総合評価とリリース判定（冒頭） | リリース可否を明示 |
| 7.4.5 Factors that blocked progress | 品質活動の概要（任意）＋進捗阻害要因 | 品質向上アクションの時系列。阻害要因は該当時のみ |
| 7.4.6 Test measures | 定量的なテスト結果 | 表＋グラフで客観的に |
| 7.4.7 Residual risks | 残存リスク | 影響・対応方針・優先度 |
| 7.4.8〜7.4.10 Deliverables / Assets / Lessons | 含めない（既定） | ユーザーが明示要求したときのみ |

## 作業手順

### Phase A: 調査と出力可否判断（既定・第1レスポンス）

**この Phase のみでレスポンスを終える。** レポート全文・Mermaid グラフ・長大な表は出さない。

1. **既存ドキュメントを読む**（テスト計画・設計・実行計画・項目表・振り返りメモ・会議議事録）。
2. **定量データを集める**（テストケース Excel／GitHub Issues TSV／CI 単体テスト集計など）。
3. **phennec** が利用可能なら `issues`・`search` 等で不具合・マイルストーンを補完する。スキーマは `mcps/user-phennec/tools/` を先に読む。
4. **出力可否判断テンプレート**（下記）に沿って、項目ごとに ○／△／× を判定する。
5. **欠損データを会話で要請する**（下記「判断材料不足時」）。× や △ の項目について、必要データ・用途・形式を列挙する。
6. **レポート全文の出力確認**を必ず行う（下記「全文出力の確認」）。ユーザーが了承するまで Phase B に進まない。

### Phase B: レポート全文出力（ユーザー了承後のみ）

ユーザーが「全文を出力して」「レポートを作成して」等と**明示的に了承**した場合のみ実施する。

1. **品質活動の事実を抽出する**（テスト実行計画のフェーズ、振り返り、議事録、Issues の検出工程・修正履歴など）。
2. **閲覧者別 HTML を 2 ファイル出力する**（下記「HTML 2 版出力」）。**長大な Markdown 全文は既定で出さない**（索引 md のみ）。
3. グラフは **Chart.js**（CDN）で描画。Mermaid は使わない。
4. 本文は**グラフ＋短いコメント**を前面に。表・詳細は `<details>` トグル内。
5. 保存先（KJDD 既定）:
   - `20_作成資料/テスト/【テスト計画】/テスト完了レポート_クライアント.html`
   - `20_作成資料/テスト/【テスト計画】/テスト完了レポート_社内.html`
   - `20_作成資料/テスト/【テスト計画】/テスト完了レポート.md`（索引のみ）

## 出力可否判断（Phase A の既定出力）

第1レスポンスは**必ずこの形式のみ**とする。コンパクトに、表中心で返す。

```markdown
# テスト完了レポート — 出力可否判断

## 参照した情報
（今回の判断に使ったソースを箇条書き。パス・ファイル名・ユーザー提供データがあれば明記）

## 項目別の出力可否

| セクション | 判定 | 根拠・現状 | 全文出力に必要な追加情報 |
| --- | --- | --- | --- |
| 総合評価とリリース判定 | ○／△／× | （例: blocker/high 0 は TSV で確認済） | （△×のときのみ記載） |
| レポート情報 | ○／△／× | | |
| テスト概要と実施体制 | ○／△／× | | |
| 実施テスト一覧 | ○／△／× | | |
| 計画からの変更 | ○／△／× | | |
| 品質活動の概要 | ○／△／× | | |
| 達成状況 | ○／△／× | | |
| テストケース実行状況 | ○／△／× | | |
| 不具合検出状況 | ○／△／× | | |
| リソース消費状況 | ○／△／× | | |
| 残存リスク | ○／△／× | | |

**判定の意味**
- **○ 出力可**: 現時点のデータで確定値まで記載できる
- **△ 一部可**: 骨格・一部数値は書けるが、確定に必要なデータが欠ける（プレースホルダや省略が発生）
- **× 不可**: 根拠データがなく、事実ベースで書けない（省略する想定）

## 追加でいただきたい情報（△・× の項目を集約）
（箇条書き。各項目に「用途」「形式の例」を添える）

## 次のアクション
レポート全文（表・Mermaid グラフ込み）の出力は、ご確認後に行います。
**全文を出力してよいですか？** 不要なセクションがあれば、その旨もお知らせください。
```

### 出力可否判断のルール

- **推測で ○ にしない。** 根拠ソースを「根拠・現状」列に 1 行で示す。
- **数値のプレビューは最小限**（例: 「実バグ 275 件」程度）。詳細表・グラフは Phase B まで出さない。
- ユーザーが会話中に追加データを渡した場合は、判断結果を更新して再提示する（全文は依然として了承後）。
- Phase A のレスポンスに、レポート全文の一部を「先行出力」しない。

## 全文出力の確認（必須）

- 初回依頼・データ追加後・判断更新後を問わず、**Phase B に入る前に必ずユーザーへ確認する。**
- 確認文の例: 「上記の判断結果をもとに、レポート全文（表・グラフ込み）を出力してよいですか？」
- 以下のときのみ Phase B を実行する:
  - ユーザーが「全文出力して」「作成して」「OK」等と**明示的に了承**した
  - ユーザーが「○ の項目だけ」「△ は省略」等、**出力範囲を指定**した（指定範囲のみ Phase B）
- 以下のときは Phase B を実行**しない**:
  - 初回依頼のみで、了承の返答がない
  - ユーザーが「判断だけ」「可否だけ」等と依頼した
  - 追加情報の提供を待っている状態

## HTML 2 版出力（Phase B 既定）

**人間が把握できる情報量**を最優先する。1 ファイルに全データを載せない。

### 版の使い分け

| 版 | ファイル名（KJDD） | 想定読者 | 分量目安 | 主目的 |
| --- | --- | --- | --- | --- |
| **クライアント提示用** | `テスト完了レポート_クライアント.html` | 発注者・意思決定者 | **スライド 3 ページ相当** | リリース可否・品質の要点を短時間で理解 |
| **社内共有用** | `テスト完了レポート_社内.html` | PM・QA・開発リード | スクロール 5〜7 セクション | **本 PJ の改善**・**次 PJ への横展開** |

各セクション冒頭に **誰向け / どう役立つか** を 1 行で書く（`.for-whom` 相当）。

### クライアント提示用（3 ページ構成）

| Page | 見出し | 前面に出すもの | トグルに隠すもの |
| --- | --- | --- | --- |
| 1 | 品質評価とリリース判定 | 判定文・KPI 4 個・**品質収束（週次・社内版と同型）**・**重大障害対応実績**・領域別判定表 | 判定根拠・high 全件一覧 |
| 2 | 実施テストと品質要点 | 1 グラフ・テスト規模サマリ | 実施テスト全一覧 |
| 3 | 残存リスクと監視 | 未完了グラフ・監視 3 行 | 未完了不具合一覧 |

**含めない**: 改善提案の詳細、横展開マトリクス、体制表、バグ分類全表、再テスト NG の構造分析。

### クライアント版の品質解釈（必須・再現ルール）

クライアント向けは**事実の羅列だけでは不十分**。品質に詳しくない意思決定者が「なぜリリースしてよいか」を読み取れるよう、**各主要データの直後**に解釈を置く。社内版には同ブロックを置かない（専門家向けのため）。

**HTML 実装**

```html
<div class="quality-read">
  <strong>品質の見方 — （データの名称）</strong>
  <p>（2〜4 文。専門用語は平易語に言い換える）</p>
</div>
```

Page 1 冒頭に `.doc-intro` で「数値の直後に品質の見方を記載」と案内する。

**配置（最低限）**

| Page | データブロック | 品質の見方で書くこと |
| --- | --- | --- |
| 1 | 総合判定（verdict） | 計画書のリリース基準を満たすこと、残存が軽微であること |
| 1 | KPI 4 個 | blocker/high 0・テスト規模・残 7 件の意味を業務影響で説明 |
| 1 | 不具合対応率（doughnut） | 97%超の修正完了が何を意味するか、残りが阻止要因でない理由 |
| 1 | 品質収束（週次グラフ） | 新規検出の減少＝品質安定のサイン（棒・折れ線の読み方） |
| 1 | 重大障害対応実績 | 決済・注文などクリティカル領域が解消済みであること |
| 1 | 領域別評価表 | 主要 4 領域すべて「可」の意味 |
| 2 | テスト規模（グラフ＋表） | 手動＋探索的＋単体の三層で厚みがあること |
| 3 | 未完了 7 件（棒グラフ） | medium 以下のみ、機能停止リスクがないこと |
| 3 | リリース後監視表 | 本番差異にも備えた運用監視があること |

**文体ルール**

- **事実→意味→リリース判断**の順で 1 段落にまとめる。
- 専門用語（blocker / high / Phase2 等）は**初出で平易語を添える**（例: 「blocker＝業務が止まるレベル」）。
- 数値はデータと**一致**させる。解釈で新しい数値を捏造しない。
- 推測や一般論だけの段落にしない。直前のグラフ・表に紐づける。
- 1 ブロック **2〜4 文・120 字前後**を目安（長文化しない）。

**セルフチェック（クライアント版）**

- 前面のグラフ・主要表それぞれに `.quality-read` があるか
- 品質の見方だけ読んで「なぜリリース可か」の筋が通るか
- 社内版に `.quality-read` が混入していないか

### 社内共有用（改善・横展開軸）

| セクション | 前面 | トグル |
| --- | --- | --- |
| サマリ | KPI 4 個・1 行インサイト（**品質収束へのリンク**を含む） | — |
| **品質収束** | 週次新規（棒）+ 累積（折れ線）の複合チャート・収束判断材料表 | 週次データ表・集計方法の注記 |
| 定量結果 | グラフ 2〜4 個＋**図の読み方**（各 1 文） | 各グラフの数値表 |
| 品質活動 | 効いた施策 5 行タイムライン | 詳細フェーズ表 |
| **本 PJ の改善** | 優先付きアクションカード 3〜5 件 | 未完了一覧 |
| **本プロジェクトからの学び** | 横展開カード 3〜5 件（カテゴリ・共有理由付き） | 重要度×優先度表 |
| 残存リスク | 監視表（4 行程度） | — |
| 詳細データ | 見出しのみ | 達成状況・不具合全表・テスト一覧・体制 |

**改善策と優先順位**: クライアント版には独立セクションを置かない。社内版では「本プロジェクトの改善」「本プロジェクトからの学び」に分け、表形式 + 優先度色分け + 人月見積で記載する。

### HTML 実装ルール

- **単一 HTML ファイル**（CSS/JS インラインまたは同一ファイル内）。Chart.js は CDN（`chart.js@4`）。
- **グラフ**: `<canvas>` + Chart.js。ドーナツ/棒を基本。各グラフの直後に **1〜2 文のコメント**（何がわかるか）。**クライアント版**はコメントに加え `.quality-read`（品質の見方）を必須とする。
- **詳細表**: 必ず `<details><summary>…</summary>…</details>` 内。summary 文言は「○○の詳細を表示」等。
- **相互リンク**: 各 HTML フッターからもう一方へリンク。
- **索引 md**: 2 HTML へのリンク・判定 1 行・参照ドキュメントのみ。長文は載せない。

### 情報量の上限（セルフチェック）

- クライアント版: 印刷 **3 ページ相当**（`.quality-read` により縦長になる場合あり）。表は **1 セクション 1 表**まで。品質解釈ブロックの省略は不可。
- 社内版: 前面テキストは **セクションあたり 150 字 + グラフ**。詳細はすべてトグル内。
- 同じ数値を **グラフと表の両方に前面表示しない**（前面=グラフ、表=トグル）。
- **詳細データは省略しない**（トグル内に集約。重複・不要データのみ排除）。

## 表現ルール（レビュー反映・必須）

人間が短時間で把握できるよう、**色・グラフ種別・表構造**に意味を持たせる。

### サマリ（KPI）

| ルール | 内容 |
| --- | --- |
| リリース判定 | 他 KPI と同列に並べない。**独立した verdict ボックス**（緑系）で最上段に表示 |
| KPI の色分け | テスト実施=青、バグ検出=橙、残存=灰、参考指標=紫 等、**意味ごとに色を変える** |
| サマリに載せる指標 | **実施テスト数 + 探索的（件数不定） / バグ検出数 / 残存数**。再テスト NG 率はサマリに載せない（詳細データへ） |
| 参考指標 | 「約 N 件のテストに 1 件のバグ」（手動テスト数 ÷ バグ数）を参考として記載可 |
| 禁止ラベル | 「読み方」→ **「要点」** に統一。「誰向け — …」のメタ説明は前面に載せない（読者が迷う） |

### グラフ

| データの意図 | グラフ種別 | キャプション |
| --- | --- | --- |
| 構成比・比率 | **doughnut** | 「図N（比率）: …」 |
| 件数・推移・比較 | **bar** / **bar+line 複合** | 「図N（件数）: …」 / 「図N（推移）: …」 |
| 品質収束 | **bar（週次新規）+ line（累積）** | 社内: 週次フル / クライアント: 月次集約可 |
| doughnut サイズ | `maintainAspectRatio: false` + **固定 height** + `cutout: '58%'` | 複数 doughnut のサイズを揃える |

**数値の見せ方（種別で分ける）**

| グラフ種別 | 数値の置き場 | 禁止 |
| --- | --- | --- |
| **doughnut** | 中央に合計（`centerText` プラグイン）＋直下の **value-legend**（色・ラベル・件数・%） | スライス内への `datalabels`（狭い扇形で視認性が悪化する） |
| **bar（縦）** | 棒の上に件数（`datalabels`） | — |
| **bar（横）** | 棒の右に件数（`datalabels`） | — |
| **収束チャート** | 軸・凡例・キャプションで読む。棒/折れ線上のラベルは原則オフ | 週次 12 点すべてにラベル |

```html
<script src="https://cdn.jsdelivr.net/npm/chartjs-plugin-datalabels@2.2.0/dist/chartjs-plugin-datalabels.min.js"></script>
<script>Chart.register(ChartDataLabels);</script>
```

**value-legend の HTML 構造**（doughnut 直下）:

```html
<div class="value-legend" id="legendX"></div>
<!-- JS: 色ドット + ラベル + 「件数（XX.X%）」を grid 2 列で描画 -->
```

doughnut は Chart.js `legend: { display: false }` とし、**value-legend が唯一の構成比ラベル**とする。

トグル内の数値表は監査用に残すが、**前面グラフ + value-legend / 棒ラベルだけで主要数値が読める**ことを Phase B セルフレビューで確認する。

### 品質収束（リリース根拠の強化）

リリース判定は「blocker/high 0」だけでは弱い。**品質が安定してきた根拠**を独立セクションで示す。

| 要素 | 社内版 | クライアント版 |
| --- | --- | --- |
| 配置 | `#convergence` セクション（サマリ直後） | Page1（品質収束 + 重大障害対応実績） |
| グラフ | 週次新規（棒）+ 累積検出（折れ線） | **社内版と同型の週次グラフ** |
| 判断材料表 | 重大障害残存・新規検出減少・対応進捗・テスト厚み | 同上 ＋ 重大障害対応実績表 |
| 重大障害対応実績 | blocker 全件 + high 全件（`<details>`） | blocker 前面 + high 分類サマリ + 全件トグル |

**データ源と注記（必須）**

- 起票日が TSV にない場合: GitHub Issue # を検出時期の参考として週別集計し、**推定である旨**を `criteria` 段落に明記する。
- テスト期間（例: 1/27〜4/20）に週を線形対応させる方法を書く。
- 起票日が取得できたら週次データを差し替える。
- 月次集約する場合は **合計が実バグ総数と一致**することをセルフレビューする。

**サマリ要点**に「週次新規検出の減少」「blocker/high 未対応 0 の維持」を 1 文含め、品質収束セクションへリンクする。

### 重大障害（blocker / high）の記載

リリース安心材料として、**具体的な内容と解消時期**を示す（件数だけでは不十分）。

| 要素 | ルール |
| --- | --- |
| データ源 | Issues TSV（Title・優先度・Status・バグ分類・URL） |
| 前面（クライアント） | **blocker 全件**（2 行）を表で記載。high は**分類サマリ**（件数・代表例・解消時期の目安） |
| 詳細 | high 全件を `<details>` 内の表に（#・要約タイトル・分類・検出週・解消確認・解消時期） |
| 検出週 | TSV 行順をテスト期間 12 週に線形対応した**推定**（※注記必須） |
| 解消確認 | Status を読み替え: `完了`→修正完了、`再テスト完了`→再テスト合格 |
| 解消時期 | GitHub `closed_at` が取れない場合: **実行計画の Phase2（〜3/19）**・**UAT 期（〜4/17）**・**本番検証後（3月）**（タイトルに「本番環境」がある場合）で表現。日付を推測で捏造しない |
| 整合チェック | blocker 2 + high 32 = 34、未対応 0、TSV の Status がすべて完了系であること |

社内版は `#convergence` 内に blocker 表 ＋ high 全件トグルを置く。

### 品質活動

- 前面は **表のみ**: `日付 | 背景 | 品質向上施策 | 効果（品質への寄与）`
- タイムライン箇条書き + 別トグル表の二重構造は禁止（意味が重複してわかりにくい）

### 改善・学び（社内版）

| セクション名 | 列 |
| --- | --- |
| 本プロジェクトの改善 | 優先度（色付き）\| タイトル \| 詳細・理由 \| 期待効果 \| 暫定コスト（人月） |
| **本プロジェクトからの学び**（旧「横展開」禁止） | カテゴリ \| 優先度（色付き）\| タイトル \| 概要 \| 共有理由 |

- 優先度 **高=赤系背景、中=橙系、低=灰系**。タグ文字だけで区別しない（見た目で判別可能に）
- 「なぜその優先度か」は **詳細・理由 / 共有理由** 列に必ず書く

### 残存リスク

- 冒頭に **選定基準** を 1 段落（何をもってリスト化したか）
- 列: 優先度 \| リスク \| 選定根拠 \| 監視内容 \| 対応策 \| 暫定コスト（人月）
- 既存機能（例: 決済失敗通知）がある場合は記載し、その上で **追加監視が必要な理由**（例: 成功率トレンド）を明記

### 詳細データ

- **データ省略 NG**。トグル内に集約するだけ。
- 「全 N 種」等の件数表記は **セルフレビューで行数を検証**（14 種なら 14 行）

### クライアント版トグル

- 「判定根拠の詳細」は Page1 サマリ（領域別判定表・KPI）の **裏付け** として同粒度の表を載せる。箇条書きだけでは不十分
- トグル内は**事実（数値表）**に限定。品質の見方はトグル外（前面）に置く

### 数値のセルフレビュー

- 表の行数・合計・割合の整合、グラフ data とトグル内表の一致を Phase B 提出前に確認

| --- | --- | --- |

## テスト概要と実施体制のルール

- **独立した「概要」見出しは設けない。** 旧「概要」で書いていた対象システム・実施期間・実施規模は、本見出しの冒頭 2〜4 文にまとめる。他セクションほど重要ではないが、「何に対するテストレポートか」を読み手に示し、以降の記述の観点を安定させる目的とする。
- 冒頭文には**品質の結論・リリース判定を書かない**（それらは「総合評価とリリース判定」に集約する）。
- 基本的にはテスト計画やテスト設計の内容を踏まえ、システムの概要、品質を向上させるためのポイントをまとめて提示する。**この段階では勝手に作成せず、必ず既存ドキュメントの表現方法に準拠しなさい。**
- なるべくコンパクトに表現できるように調整しなさい。
- チーム体制・対象システム名・重点領域は計画書の用語をそのまま使う（例：KJDD では「デザイン作成機能」「決済機能」）。

## 品質活動の概要のルール

- **目的**: 読み手が「品質を保つために何を動かしたか」を結果論だけでなくプロセスとして把握できるようにする。
- **書き方**: 時系列（フェーズ・週・マイルストーン単位）で 3〜8 行程度に圧縮する。各セルは 1〜2 文。箇条書きの羅列にしない。
- **必須の列**: `わかったこと` / `実施したアクション` / `その後の状態`。事実と因果が追えること。
- **記載例の型**（事実がある場合のみ）:
  - わかったこと: 「Phase1 で認証に blocker が 2 件」「再テスト NG 率が約 12%」
  - アクション: 「認証を初日最優先に変更」「修正出口に近傍パターン確認を追加」
  - 状態: 「blocker 0・high 未対応 0」「注文系テスト着手可能に」
- **根拠ソース**: テスト実行計画、振り返りメモ、議事録、Issues TSV の検出工程・ステータス推移など。**ドキュメントにない活動は書かない。**
- **社内版**: 効いた施策を **5 行以内のタイムライン**で前面に。詳細フェーズ表は `<details>` 内。
- **クライアント版**: 品質活動の詳細は載せない（Page2 でテスト規模のみ）。
- 横展開・改善提案は **社内版の専用セクション**へ（品質活動の概要には混ぜない）。

## 用語: スクリプト化手動テスト（KJDD）

| 含む | 含まない |
| --- | --- |
| 手順・期待結果が文書化された手動テストケース | 探索的テスト（件数不定） |
| 手動結合テスト（デザイン・EC・管理画面） | モンキーテスト |
| 補強テスト（金額・メール・FLUX・カートマージ等） | 単体テスト（CI 自動。別行で記載） |

「スクリプト化テスト」だけと書くと単体テストと混同しやすいため、**スクリプト化手動テスト** と明記する。

| 含む | 含まない |

| 補強テスト（金額・メール・FLUX・カートマージ等） | 単体テスト（CI 自動。別行で記載） |

## 定量的なテスト結果のルール

- 数値は根拠ソースを示す（Issues TSV 名、Excel、CI 集計など）。トグル内の表に出典を記載。
- 解釈の余地のない表現にする。
- **前面=グラフ+コメント、詳細=トグル内の表**（同じ数値を両方に並べない）。

## 定量データの可視化（HTML + Chart.js）

**既定は Mermaid を使わない。** HTML レポートでは Chart.js（CDN）でグラフを描画する。

### 基本方針

- **前面**: `<canvas>` グラフ + **図の読み方**（1〜2 文）。
- **詳細**: `<details>` 内の数値表（監査・引用用）。
- グラフタイトル・出典を Chart.js `plugins.title` またはキャプションで付ける。
- データ欠損系列はプロットしない。

### Chart.js 推奨

CDN: `chart.js@4` + **`chartjs-plugin-datalabels@2`**（件数・割合をグラフ上に表示）

| データ | チャート種別 | 配置 |
| --- | --- | --- |
| **品質収束** | bar + line（週次） | 社内・クライアントとも同型 / Page1・`#convergence` |
| **重大障害対応実績** | 表（blocker 前面 + high トグル） | 社内・クライアント: 品質収束直下 |
| 優先度別不具合 | doughnut + centerText + value-legend | 社内: 前面 |
| 検出工程別 | doughnut + centerText + value-legend | 社内: 前面 |
| 対応状況 | bar + datalabels | 社内: 前面 |
| 発生原因上位 | horizontal bar + datalabels | 社内: 前面 |
| 不具合対応率 | doughnut + centerText + value-legend | クライアント: Page1 |
| テスト規模（カテゴリ別） | doughnut + centerText + value-legend | クライアント: Page2 |
| 未完了件数 | bar + datalabels | クライアント: Page3 |

### Mermaid について

Markdown プレビューでの Syntax Error が多発するため、**Phase B では Mermaid を使わない**。ユーザーが明示的に Markdown 版を求めた場合のみ、互換性の高い `flowchart TD` / `pie showData`（英語ラベル）を検討する。

### インタラクティブ表示

フィルタ・ホバーが必要なときは [canvas スキル](../skills-cursor/canvas/SKILL.md) を検討。既定は HTML + Chart.js。

## 残存リスクのルール

テスト期間中に解決しなかった、あるいは発見されたが許容された残存リスクを明確にする。リスクごとに想定される影響範囲と今後の対応方針を示し、優先度も明記する。

## 判断材料不足時の対応

### 会話での資料要請（必須）

リポジトリ・phennec から取得できないが、レポート品質のために有用なデータがある場合は、**Phase A の「追加でいただきたい情報」に列挙して要請する。** 黙って `【要記入】` だけ残して終わらせない。全文出力の了承前に、必要データを先に提示する。

要請文の型:

> 「テスト完了レポートの ○○ セクションを確定するため、以下のデータが必要です。ご提供いただけますか？
> - 必要データ: （例: Excel のカテゴリ別 実施数・合格数・不合格数）
> - 用途: 達成状況・テストケース実行状況の確定
> - 形式: 表のコピペ、スクリーンショット、TSV 等で可
> 不要であれば当該項目はレポートから省略します。」

### 典型的にユーザー提供が必要なデータ（KJDD）

| 項目 | 用途 | 省略可否 |
| --- | --- | --- |
| Excel 手動テストの実施数・合格数・不合格数・未実施数 | 達成状況・実行状況・合格率 | 省略可（セクション簡略化） |
| UAT 結果・受入承認の有無 | リリース判定 | 省略可（条件付き判定のまま） |
| 性能テスト結果 | 非機能要件の達成確認 | 該当時のみ |
| 品質活動の社内メモ（会議にない判断・エスカレーション） | 品質活動の概要 | 省略可（ドキュメントにある事実のみ記載） |

### その他

- 必要がないというユーザーの回答があった場合は、作成する項目をスキップし、テスト結果レポートには含めない。
- プレースホルダ（`【要記入】`）は、**要請したうえで未提供の項目にのみ**使う。推測値は書かない。
- ユーザーが後からデータを提供したら、該当セクションの表・グラフを更新して再出力する。

## 品質ルール

- レポートは**日本語**。
- **トークン節約**: 既定は Phase A（出力可否判断）のみ。全文はユーザー了承後の Phase B のみ。
